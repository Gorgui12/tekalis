4. ARCHITECTURE
Framework & Runtime
- Runtime: Node.js (plain JavaScript, no TypeScript)
- Framework: Express.js 4.x
- Architecture style: MVC (Model-View-Controller) with service layer
- Entry point: server.js (661 lines -- monolithic, mixes config with inline admin routes)
Database
- Primary: MongoDB (via Mongoose 8.x)
- Optional: Redis (for caching -- cache.js middleware, config/redis.js)
- Connection: Atlas or local, configurable via MONGODB_URI
- Cloud Storage: Cloudinary (optional, lazy-init for images)
Authentication
- Method: JWT (JSON Web Tokens)
- Token storage: Authorization: Bearer <token> header
- Password hashing: bcryptjs with salt rounds = 12
- Token expiry: JWT_EXPIRE env var, defaults to 7 days
- Password reset: Crypto-based token (SHA-256 hashed), 10-minute expiry
Payment
- Primary: PayDunya (Senegalese mobile money -- Wave, Orange Money, Free Money)
- Secondary: Stripe (lazy-init, configured but not in package.json)
API Versioning
- All routes prefixed with /api/v1

10. SECURITY PRACTICES
Implemented well
 1. JWT secret validation -- Server refuses to start in production with weak secrets
 2. Timing attack prevention -- 200ms delay on failed login/register to prevent user enumeration
 3. Password hashing -- bcryptjs with 12 salt rounds
 4. Password field exclusion -- select: false on password field, .toSafeObject() helper
 5. NoSQL injection prevention -- express-mongo-sanitize
 6. Rate limiting -- Separate limits for API, auth, and admin routes (disabled in dev)
 7. CORS -- Whitelist-based with origin callback (allows null origin for server-to-server)
 8. Security headers -- Helmet with cross-origin resource policy
 9. Payment webhook verification -- Double verification (hash + re-confirm with PayDunya API)
10. Amount verification -- Webhook checks received amount against order total
11. Constant-time hash comparison -- crypto.timingSafeEqual for webhook hash
12. Self-deletion prevention -- Admin cannot delete their own account
13. RMA ownership verification -- Users can only see/cancel their own RMAs
14. Order ownership verification -- Order details check user ID match
11. ISSUES AND CONCERNS
CRITICAL
1. errorHandler.js is never mounted. The errorHandler and notFound middlewares exported from middlewares/errorHandler.js are never app.use()'d in server.js. Instead, server.js has its own inline error handler at lines 604-640. The asyncHandler wrapper is also never used in any controller -- all handlers use raw try/catch. This means the AppError class and asyncHandler utility are dead code.
2. Duplicate admin routes. Admin user routes exist in TWO places:
- /api/v1/users/* in userRoutes.js (lines 279-454) with isAdmin middleware
- /api/v1/admin/users/* in server.js (lines 404-601) with isAdmin middleware
Both serve the same purpose. Similarly, admin product routes exist in both productRoutes.js and server.js adminRouter. This creates confusion and maintenance burden.
3. Duplicate email utilities. utils/sendEmail.js and services/emailService.js both configure nodemailer independently. The legacy utils/sendEmail.js is a simpler version that creates a new transporter on every call (no singleton). It does not appear to be imported anywhere, but it creates confusion about which is the canonical email implementation.
4. Stock decrement is not atomic with order creation. In orderController.createOrder (line 73-84), the order is saved first, then stock is decremented via Product.bulkWrite. If the server crashes between these two operations, the order exists but stock is not decremented. There is no transaction or compensating logic. The reverse (cancellation restocking at lines 255-262) has the same issue.
HIGH
5. Regex injection in product search. In productController.getProducts (line 49), user-provided search is passed directly into $regex:
{ name: { $regex: search, $options: "i" } }
Special regex characters in user input (e.g., .*, ()+) could craft expensive regex patterns (ReDoS) or alter the query semantics. The same issue exists in orderController.getAllOrders (line 158), userRoutes.js admin search (lines 417-419), and categoryController brand filter (line 44). User input should be escaped with a regex-safe function before use.
6. body-parser is redundant. body-parser is listed as a dependency but express.json() and express.urlencoded() are used directly (which include body-parser since Express 4.16). The dependency should be removed.
7. Missing authorization checks on admin inline routes. The admin category CRUD routes in server.js (lines 280-303) directly pass req.body to Category.create() and findByIdAndUpdate() without any input validation. An admin could inject arbitrary fields into a category document.
8. forgotPassword token is never emailed. The forgotPassword handler in authController.js (line 205) logs the reset URL to console with console.log and has a // TODO: envoyer l'email comment. The email is never actually sent, making the password reset flow non-functional in practice.
9. Missing redis package in package.json. Both config/redis.js and middlewares/cache.js call require("redis") at module load time. If Redis is not installed, this will crash the server. Unlike Cloudinary/Stripe which use lazy init, Redis connects eagerly.
10. Cache middleware creates its own Redis client. middlewares/cache.js (line 5) creates a completely separate Redis connection instead of importing from config/redis.js. This means two Redis connections exist, and the cache middleware will fail if Redis is not installed even though config/redis.js has retry logic.
MEDIUM
11. server.js is monolithic (661 lines). The admin router with ~400 lines of inline handlers is defined directly in server.js. This should be extracted to a dedicated adminRoutes.js file with proper controller delegation.
12. No input validation on many admin routes. Routes like POST/PUT for categories, settings, promo-codes, and admin user management pass req.body directly to Mongoose without express-validator or manual sanitization.
13. No Swagger/OpenAPI documentation. No API documentation exists. For a project of this size, this makes frontend integration harder.
14. No test suite. The test script is a placeholder. There are zero test files in the project. No testing framework (Jest, Mocha, etc.) is installed.
15. No Docker configuration. No Dockerfile or docker-compose exists for containerized deployment.
16. No linter or formatter configuration. No .eslintrc, .prettierrc, or equivalent exists.
17. Sitemap has a bug. In routes/sitemap.js (line 74), Articles are queried with { stock: { $gt: 0 } }. Articles do not have a stock field -- this filter is from a copy-paste of the products query and will return all articles regardless (since undefined > 0 is never true in MongoDB, this might actually return zero articles).
18. dashboardController.js is dead code. It is never imported or used anywhere. The functionality is duplicated in routes/stats.js.
19. moment-timezone and node-cron are unused. These are listed as dependencies but are never imported in any source file. They should be removed or their usage documented.
20. helpers.js has a generateOrderNumber function that is unused. The Order model uses its own crypto.randomBytes approach. Similarly, helpers.js exports many utilities that are never imported elsewhere.
LOW
21. No graceful shutdown. process.on("unhandledRejection") exists but there is no SIGTERM handler (only SIGINT in database.js). In a production container (Docker/Kubernetes), SIGTERM is the standard shutdown signal.
22. moment-timezone could be replaced. Intl.DateTimeFormat is already used in helpers.js. Having both moment and Intl is unnecessary bloat.
23. notification.js model is lowercase while all other models use PascalCase filenames. This is a consistency issue.
24. No request ID / correlation ID. Error logs have no request ID to help trace issues across multiple concurrent requests.
25. Sitemap categories are hardcoded (lines 30-40 of sitemap.js). If categories change in the database, the sitemap will be stale. Should query from the Category model.
26. Rate limiting is entirely disabled in development. The createLimiter function (line 94-98) returns a no-op middleware when NODE_ENV !== "production". This means any dev environment testing is unprotected, which could mask rate-limiting-related issues.
27. The analytics admin endpoint (line 396-398 in `server.js) is a stub returning empty data.
SUMMARY
Tekalis-backend is a functional Express.js e-commerce backend for the Senegalese market, built with MongoDB/Mongoose, JWT auth, PayDunya mobile money, and Cloudinary image hosting. The codebase shows good awareness of security concerns (timing attacks, NoSQL injection, JWT validation, webhook verification) but suffers from several architectural and quality issues.
Strengths:
- Solid security foundations (bcrypt, JWT, helmet, mongo-sanitize, rate limiting, timing-safe comparison)
- Well-designed Mongoose schemas with proper indexes, validation, and pre-save hooks
- Race-condition-safe order/RMA number generation using crypto.randomBytes
- Lazy-init pattern for optional services (Cloudinary, Stripe)
- Comprehensive email template system
- PayDunya webhook with double verification (hash + API re-confirm)
Priority fixes needed:
 1. Remove dead code (errorHandler, dashboardController, sendEmail.js, unused dependencies)
 2. Extract admin routes from server.js into dedicated files
 3. Fix regex injection in search queries (escape user input)
 4. Implement email sending in forgotPassword flow
 5. Add atomic stock management (transactions or compensating logic)
 6. Remove Redis eager loading or install the redis package
 7. Add input validation on all admin routes
 8. Add tests (at minimum integration tests for critical flows)
 9. Add Docker support for production deployment
10. Add API documentation (Swagger/OpenAPI)
